# Owner monitoring

The existing administration shell includes AI Monitoring, Storage Monitoring, Security Center, Performance Monitoring, Error Monitoring, Notifications, and Admin Settings. These sections are linked from `/admin` using the `section` search parameter. Phase 1 user management, activity, analytics and audit routes remain available.

The configured Owner ID is still the only owner authority. The new `/api/monitoring` endpoint independently verifies Identity, current database account status and owner authorization on every request. Ordinary administrators cannot read monitoring data. Settings and issue changes require a same-origin request and create an audit record in the same transaction. Reports use parameterized filters, bounded pages and fixed sort choices. CSV summaries neutralize spreadsheet formulas and exclude raw events and student content.

## Collection

AI instrumentation records only validated action names, provider/model, duration, HTTP status, safe error codes and the provider's actual input, output and cached token counters. No prompt, source, question, completion or conversation is recorded. Model pricing defaults to unavailable. The owner can configure verified USD input/output/cached rates per million tokens for the existing OpenAI model. Cost estimates use `(uncached input × input rate + cached input × cached rate + output × output rate) / 1,000,000`. Missing usage or pricing is excluded; estimates are recalculated using current configured rates and are not invoices.

Document inventory queries select only sizes, MIME types, user IDs and timestamps. Upload validation failures, storage failures, successful uploads and deletions produce safe operational measurements. No document filenames, extracted text, blob keys or download URLs enter reports. Current inventory is a snapshot, while new upload/delete trends start with this deployment. A scheduled sample records total stored document bytes every 15 minutes; the consumption chart uses the last observed sample per day. Uploaded-today/month counters use recorded successful upload events, including subsequently deleted files. Monthly net changes cover observed operations; account deletion cleanup and activity before collection began are excluded. A configured storage planning quota is not a provider-reported quota. Actual provider capacity is unavailable.

The Security Center reuses existing server-generated login, failed sign-in, registration, verification, recovery request and administrative audit events, plus observed API authorization failures. Suspension/reactivation remains in User Management with the existing audit and API enforcement. Current Identity hooks do not expose session expiry, completed password resets, provider-wide login failures or provider session revocation; the UI states these limitations. No password or token storage was added.

Authenticated browser exception and unhandled rejection listeners send only a fixed event category. React route errors send the same safe category-only report. These are unverified client reports, rate limited separately. Error messages, stack traces, URLs, query strings and browser contents are deliberately excluded. Backend handlers record response status and elapsed duration; failures group by fixed technical category, feature, HTTP status and deployment environment. Telemetry writes fail open so monitoring outages do not turn successful study operations into failures. A database outage can prevent both the original query and its telemetry from being persisted.

## Service checks and alerts

The scheduled monitoring function runs every 15 minutes on published deploys. It reads Identity settings, runs `SELECT 1`, lists a reserved Blobs prefix, and requests the application root. Each observation is scoped to that operation. AI health is based on the latest real provider request in the preceding 15 minutes, with unknown status when idle. Function health proves that scheduled execution ran. Observations expire visually after 30 minutes. These checks are not an end-to-end sign-in or upload transaction and do not establish a contractual availability percentage.

Thresholds cover failed logins, authorization failures, server API failures, upload failures, AI failures, daily AI request volume, overall request volume, administrative action volume and planning quota utilization. Volume rules are review signals, not assertions of malicious behavior. Notifications are persistent and grouped by condition, with at most one occurrence increment per hour for threshold alerts. Service probe failures are grouped by service. The Owner can mark records read, resolve or reopen them. A recurrent failure reopens a resolved issue. Email delivery is not configured.

The daily retention function removes telemetry and issues after 90 days; existing audit retention remains 365 days. Account deletion also removes raw user telemetry. Grouped operational issues contain no user identity or content.

## Deployment and validation

Two operational tables are introduced by additive generated migrations, including a 64-bit byte counter for aggregate storage inventory. The existing applied migrations are unchanged. The platform applies the new migration during deployment; it must land before runtime reports can query the new tables. No migrations are applied manually and no production build is run by this task. Scheduled health history begins only on a published deploy, so previews display unknown service observations until records are available.

Type checking, lint and unit tests cover existing features plus owner-only authorization, query parameterization, metadata-only storage queries, CSV formula safety, settings validation, unavailable usage counters and fail-open telemetry. All 18 core report query variants were also validated with read-only Postgres EXPLAIN using typed empty telemetry CTEs and existing account tables. Live scheduled probes, Identity provider operations and new-table database execution require validation after platform deployment. Query-level database instrumentation and external provider status feeds are not implemented; database probe duration and total API handler duration are available.
